## 3-ب. ★ ما نُفِّذ فعلياً

### الملف الجديد

`test/security-rules/permission-matrix.test.js` — مصفوفة مُعطاة بالبيانات،
صفٌّ واحد لكل مفتاح يحمل عمليةً واحدة، يُشتقّ منه اختباران:

```
السماح : { ...المفاتيح المساعدة, [المفتاح]: true } ⟵ يجب أن ينجح
المنع  : { ...المفاتيح المساعدة }                  ⟵ يجب أن يُرفض
```

★ **والعمليات مشتقّة من `firestore.rules` نفسها لا مخترَعة** — كل حمولة
تستوفي بقية شروط مسارها حرفياً (النطاق · وقت الخادم · الحقول السحابية
الممنوعة · السبب النصي · المسارات المقيَّدة).

### التوزيع

| القسم | المفاتيح | ملاحظة |
|---|:-:|---|
| 2.1 البيانات الأساسية | 5 | إنشاء |
| 2.2 التوريد | 8 | قراءة · إنشاء · **أربعة مسارات مقيَّدة** على الجونية |
| 2.3 التسعير والصرف | 9 | يشمل المستند الفرعي `pricing/current` |
| 2.4 الإتلاف والجرد | 2 | + سبب نصي |
| 2.5 التحصيل والذمم | 6 | يشمل مسار الإيداع بصلاحيتيه معاً |
| 2.6 السحبيات والخرجيات | 5 | **سجلّان بصلاحيات منفصلة** |
| 2.7 المالية والرقابة | 6 | شروط قراءة · و`sourceNetImpactView` مستثنى بمبرر |
| 2.9 التعديل والإلغاء | 20 | عشر وحدات × (تعديل + إلغاء) |
| **الإجمالي** | **61** | **× اتجاهين = 122 اختباراً** |

**والمستثنيان** هما نفسهما استثناءا بوابة التغطية بمبرريهما الموثَّقين:
`sourceNetImpactView` و`messagingSend`.

### ★ حارس ضد تآكل التغطية

اختبار ثالث يقابل صفوف المصفوفة بمفاتيح `firestore.rules` **في الاتجاهين**،
ويرفض التكرار.

> ★ **ولماذا يُقاس على القواعد لا على الكتالوج:** `check:coverage` يضمن أصلاً
> تطابق الكتالوج والقواعد في الاتجاهين — فالقياس على القواعد **يكافئه
> ويقيس سطح التنفيذ الفعلي**.

### ★ ولم يُقبَل الحارس على كلمته — اختبار طفرة

⛔ **حارس لا يفشل أبداً لا قيمة له.** فحُذف صفّ `expenseView` مؤقتاً وأُعيد
التشغيل:

```
# tests 166 · # pass 165 · # fail 1
مفاتيح تفرضها القواعد بلا صفّ: expenseView
```

★ **رصده الحارس وسمّاه صراحةً**، ثم أُعيد الصفّ وعاد التشغيل إلى 168/168.

### إصلاح تشغيلي مصاحب

`run-rules-tests.mjs` صار يشغّل ملفَّي الاختبار بـ`--test-concurrency=1`،
لأن كل ملف يعمل في عملية مستقلة ويستدعي `clearFirestore()` على **المحاكي
نفسه** — فالتوازي يجعل أحدهما يمسح بيانات الآخر تحت قدميه.
