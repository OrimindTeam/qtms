# ADR-0001: تطبيق Flutter متصل مباشرةً بقاعدة بيانات سحابية مستندية، بلا خادم مستقل

**الحالة:** مقبول
**التاريخ:** 2026-08-21
**متّخذو القرار:** مالك النشاط (CLIENT) — **قرار منصوص عليه في المستند الوظيفي §2.1 و§2.8**
**يتعلق بمتطلب:** `NFR-COMPAT-01` · `NFR-COST-01` · كل المتطلبات الوظيفية

> **ملاحظة على الحالة:** هذا ADR **نقل لقرار مُتَّخذ فعلاً وموثَّق بثقة كاملة
> في المستند المصدر**، لا اقتراح من Claude Code — ولذلك حالته «مقبول» لا
> «مقترح». صيغته هنا للتوثيق والتتبّع لا لإعادة فتح النقاش.

## السياق (Context)

نظام مخزني/ذمم لمنشأة واحدة بفريق صغير (4–6 مستخدمين)، يحتاج:
- **مصدر حقيقة مركزياً واحداً** يراه كل المستخدمين لحظياً.
- **ذرّية صارمة** لكل عملية تمس الأرصدة (توزيع متزامن لآخر كمية).
- **تفويضاً دقيقاً على مستوى الزر والحقل** مقيَّداً بنطاق مصادر.
- **قدرة تشغيل بأقل عبء إداري ممكن** — لا فريق DevOps ولا مسؤول خوادم.
- **واجهة أندرويد عربية RTL** سريعة الاستخدام بيد واحدة.

والقيد الاقتصادي الحاكم: **المنشأة لا تملك قدرة تشغيل خادم ولا صيانته**.

## الخيارات المدروسة (Options Considered)

### الخيار 1: خادم تطبيق خاص + REST API + قاعدة علائقية
- **الإيجابيات:** تحكم كامل في منطق الأعمال · معاملات علائقية ناضجة ·
  استقلال عن مزوّد بعينه · **منطق التفويض في مكان واحد مألوف**.
- **السلبيات:** يحتاج **بنية تحتية وصيانة ونسخاً احتياطياً ومراقبة وشهادات
  وتحديثات أمنية** — كلها أعباء تشغيلية دائمة على منشأة بلا فريق تقني ·
  **نقطة فشل واحدة** يديرها الفريق نفسه · كلفة ثابتة شهرية بغض النظر
  عن الاستخدام · زمن تطوير أطول (طبقة API كاملة تُبنى وتُختبَر وتُوثَّق).
- **مرفوض:** العبء التشغيلي **يفوق المكسب** لحجم هذا النظام وفريقه.

### الخيار 2: تطبيق Flutter متصل مباشرةً بمنصة سحابية مُدارة *(المعتمد)*
- **الإيجابيات:** **لا خادم يُدار** · معاملات ذرّية بإعادة محاولة تلقائية
  تعطي عملياً نفس ضمان القفل · **قواعد حماية تُنفَّذ داخل بنية القاعدة
  نفسها** فترفض الطلب حتى لو أُرسل من خارج التطبيق · مصادقة ومطالبات
  مخصّصة جاهزة · دوال سحابية لما لا يُؤتمَن عليه الجهاز · **تكلفة بالاستخدام
  لا ثابتة** · زمن تطوير أقصر.
- **السلبيات:** **ارتباط قوي بمزوّد بعينه (Vendor Lock-in)** · **قاعدة
  مستندية لا علائقية** فلا توجد قيود مفتاح أجنبي ولا استعلامات ربط —
  والتصميم يعوّضها بالتكرار المقصود للأسماء والفهارس المركّبة ·
  **التكلفة تتناسب مع عدد القراءات والكتابات** فتحتاج انضباطاً تصميمياً ·
  منطق التفويض **موزّع** بين قواعد الحماية والدوال.
- **مقبول:** السلبيات **معروفة ومُدارة صراحةً** في التصميم (`ADR-0008`
  للتكلفة · `ADR-0005` و`ADR-0007` لغياب العلاقات).

### الخيار 3: قاعدة بيانات محلية على الجهاز مع مزامنة
- **الإيجابيات:** يعمل بلا اتصال · سرعة استجابة قصوى.
- **السلبيات:** **قاتل لنظام ذمم متعدد المستخدمين**: مستخدمان يوزّعان آخر
  كمية بلا معرفة أحدهما بالآخر ⟵ **رصيد سالب وذمم خاطئة**، ولا حل لتعارض
  المزامنة إلا بقرار بشري في كل حالة.
- **مرفوض:** يناقض جوهر النظام — راجع `ADR-0003`.

## القرار (Decision)

**تطبيق أندرويد بـ Flutter/Dart يتصل مباشرةً بـ Cloud Firestore عبر حزم
Firebase الرسمية، بلا Backend مكتوب من الصفر ولا خادم تطبيق ولا REST API** —
لأن العبء التشغيلي لخادم خاص لا يبرّره حجم هذا النظام، **وقواعد الحماية
تعطي تفويضاً لا يقل صرامة عن كود الخادم مع صفر صيانة**.

## النتائج (Consequences)

**إيجابية:**
- لا خوادم تُدار ولا نسخ احتياطي يُجدوَل يدوياً ولا شهادات تُجدَّد.
- **التفويض يُفرَض داخل بنية القاعدة نفسها** — فيسري على أي عميل، لا على
  التطبيق وحده.
- التوسّع أفقياً تلقائي، والتكلفة بالاستخدام لا بالسعة المحجوزة.

**سلبية / مقايضات مقبولة:**
- **ارتباط بمزوّد بعينه** — مقبول لأن البديل عبء تشغيلي يومي دائم.
- **لا استعلامات ربط ولا قيود مفتاح أجنبي** — يُعوَّض بـ:
  **تكرار مقصود للأسماء داخل السطور** · **سجلات حراسة تفرد** ·
  **فهارس مركّبة مُعلَنة** (`§6.4`) · **وسلامة مرجعية تفرضها العمليات
  السحابية** لا القاعدة.
- **التكلفة محكومة بعدد القراءات والكتابات** ⟵ يفرض `ADR-0008`.
- **لا يوجد `openapi.yaml`** — مجلد `05-api/` يُستخدَم لعقد العمليات
  السحابية والمصادقة، لا لعقد HTTP.
