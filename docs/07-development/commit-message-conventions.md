# اصطلاحات رسائل الالتزام (Commits) — QTMS

| البند | القيمة |
|---|---|
| **الإلزامية** | **M** |
| **الطبيعة** | **STATIC** |
| **المالك** | DEV |
| **المعيار** | **Conventional Commits 1.0.0** |

---

## 1. الصيغة

```text
<النوع>(<النطاق>): <وصف مختصر بصيغة الأمر>

<متن اختياري — لماذا لا كيف>

<تذييل اختياري — مراجع وتغييرات كاسرة>
```

| الجزء | القاعدة |
|---|---|
| **النوع** | من الجدول في §2 — **إلزامي** |
| **النطاق** | **اسم الوحدة** من [`../04-design/module-design/`](../04-design/module-design/) — مُوصى به بشدة |
| **الوصف** | ≤ 72 حرفاً · **بصيغة الأمر** («أضف» لا «أضفت») · بلا نقطة ختامية |
| **المتن** | **يشرح السبب** — والكود يشرح الكيفية |

## 2. الأنواع

| النوع | المعنى | أثره على الإصدار |
|---|---|---|
| `feat` | قدرة وظيفية جديدة | MINOR |
| `fix` | معالجة خلل | PATCH |
| `docs` | توثيق فقط | — |
| `style` | تنسيق بلا تغيير سلوك | — |
| `refactor` | إعادة هيكلة **بلا تغيير سلوك** | — |
| `perf` | تحسين أداء | PATCH |
| `test` | اختبارات | — |
| `build` | أدوات البناء والاعتماديات | — |
| `ci` | خطوط الأتمتة | — |
| `chore` | أعمال صيانة عامة | — |
| `revert` | تراجع عن التزام سابق | حسب الملغى |
| ★ `rules` | ★ **تغيير في قواعد الحماية السحابية** | **يُعامَل معاملة `feat`/`fix` حسب الأثر** |
| ★ `schema` | ★ **تغيير بنيوي في القاعدة أو الفهارس** | **يستلزم سطر `migrations-log.md`** |

> ★ النوعان `rules` و`schema` **إضافة خاصة بهذا المشروع** — لأن قواعد الحماية
> وبنية القاعدة **هما طبقة التفويض والحقيقة الفعلية هنا**، وإخفاؤهما داخل
> `chore` يُضيّع أثرهما في التاريخ.

## 4. التغيير الكاسر

```text
feat(distribution)!: امنع أكثر من توزيعة واحدة لكل مقوت في اليوم

BREAKING CHANGE: المفتاح المركّب {dealerId}_{sourceId}_{stockDate} صار
إلزامياً — والتوزيعات القديمة بلا هذا المفتاح تحتاج ترحيلاً.
Refs: GR-18 · ADR-0006
```

| القاعدة |
|---|
| **`!` بعد النطاق + تذييل `BREAKING CHANGE:`** |
| ★ **يستلزم `ADR`** ودليل ترقية في `docs/14-maintenance/upgrade-guides/` |
| **يرفع MAJOR** وفق [`../00-governance/versioning-and-change-policy.md`](../00-governance/versioning-and-change-policy.md) |

## 5. التذييل — الربط بالتوثيق

```text
Refs:    FR-M5 · GR-18 · AT-22
Closes:  E-17
ADR:     ADR-0006
Risk:    RISK-01
```

> ★ **كل التزام يمسّ قاعدة عمل يذكر معرّفها** — هذا ما يجعل
> `requirements-traceability-matrix.md` **قابلة للتوليد من التاريخ نفسه**.

## 6. أمثلة صحيحة

```text
feat(owner-ledger): أضف صفَّي باقي الضمار قبل الخصم وبعده

يطبّق قرار OQ-001 (الخيار ج): يُعرض الصفّان معاً،
والصافي النهائي مبنيّ على «بعد الخصم».
يحلّ التعارض المقاس في سيناريو §15 (فرق 5,000 = الخصم).

Refs: FR-M15-03 · FR-M15-04
Decision: OQ-001
```

```text
fix(inventory): امنع جمع الحبات مع الأوزان في رصيد النوع

الحبة والوزن وحدتان مختلفتان — وجمعهما يُنتج رقماً بلا معنى.

Closes: E-09
Refs: GR-12
```

```text
schema(inventory): أضف stockDate لكل حركة مخزون وفهارسها

بند قبول في مراجعة المعلم M-1 — وإغفاله يجعل المرحلة الثالثة
مستحيلة بلا هجرة كاملة لبيانات مالية حيّة.

Refs: RISK-01
Migration: docs/06-database/migrations-log.md
```

## 7. أمثلة مرفوضة

| الرسالة | لماذا تُرفَض |
|---|---|
| `تحديثات` | **بلا نوع وبلا معنى** |
| `fix: إصلاح مشكلة` | **أي مشكلة؟** — بلا مرجع ولا وصف |
| `feat: أضفت شاشة التوزيع` | **صيغة ماضٍ** — القاعدة: صيغة الأمر |
| `chore: تعديل قواعد الحماية` | ★ **نوع خاطئ** — الصحيح `rules` |
| `feat: أضف حقلاً وأصلح خللين ونظّف الأسماء` | **التزام واحد لغرض واحد** |
| `fix: مفتاح API الجديد abc123` | ⛔ **سرّ في رسالة التزام** — يبقى في التاريخ للأبد |

## 8. قواعد حاكمة

| # | القاعدة |
|---|---|
| 1 | **التزام واحد = غرض واحد قابل للمراجعة والتراجع وحده** |
| 2 | ⛔ **لا سرّ ولا بيانات حقيقية في أي رسالة التزام** — التاريخ لا يُنظَّف بسهولة |
| 3 | **الرسالة بالعربية** — والمصطلحات التقنية والمعرّفات بالإنجليزية كما في [`../04-design/naming-conventions.md`](../04-design/naming-conventions.md) |
| 4 | **لا التزام «يعمل الآن»** بلا شرح ما الذي كان معطلاً |
| 5 | **ما يُدفَع على `main` يُقرأ بعد سنة** — اكتب لقارئ ذلك اليوم |
